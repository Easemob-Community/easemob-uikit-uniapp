# Android 附件修复与自发文件即时预览设计

## 目标

修复真机确认的 Android 文件发送失败（RD-16）与文件下载被明文 HTTP 拦截（RD-17），并让已成功发送的文件在当前登录周期内单击即可本地打开。接收文件和本地副本已不可用的历史文件仍走远端下载回退。

## 非目标

- 不实现单条/合并转发。
- 不新增通用下载队列、持久化下载管理页或公开消息模型字段。
- 不改变图片/视频保存相册、失败重发和复合消息既有契约。
- 不把 Android 结果外推为 iOS/鸿蒙已验证。

## 方案与取舍

### 采用：最小生命周期修复

1. Android 使用内置 `uni.chooseFile`，将返回的原始路径或 `content://` URI 直接交给 SDK，不再经自研原生插件复制或转换路径。真机确认该 URI 可直接计算 MD5 并由 `uni.uploadFile` 上传。
2. 附件下载 URL 复用统一归一逻辑，将环信 `http://` 与协议相对地址升级为 HTTPS，保留查询参数与 secret。
3. 文件发送/重发成功后暂不 release 本地副本；删除消息、其他端删除和登出仍按现有登记清理。单击和长按下载都先尝试本地打开，成功时不显示 loading，失败后再走原远端下载。
4. `fileOpen` 全端开启；H5 的 blob/data URL 不当作可直接 `openDocument` 的本地文件，仍走浏览器下载。
5. 远端下载全程只创建一个 loading，不按百分比重复调用 `uni.showLoading`，避免 Android 原生 loading 页面累积导致低内存查杀。

### 备选：新增持久化附件缓存和 `localFilePath` 公共字段

能覆盖更完整的跨重启缓存，但会扩大公开类型、缓存失效与账号隔离范围。本轮只要求自发文件即时预览，现有 `url + releaseByPath` 已足够，因此不采用。

### 排除：仅让单击调用远端下载

改动最小但仍会出现 loading，不满足“自己发的点击直接预览”的核心要求。

## 约束

- 纯 TS、零新增运行时依赖、平台差异留在 provider/platform/download 层。
- 不修改 easemob-uikit-vue 参照仓库。
- 发送成功的文件只在当前登录周期和消息生命周期内保留；进程结束或系统回收后允许回退远端。
- 本地打开失败不能吞掉远端回退；只有本地打开成功才跳过下载 loading。

## 验收

- 新增 Node 回归测试先 RED 后 GREEN，覆盖 file URI、HTTPS/secret、发送后保留/删除清理、本地路径判定与本地打开。
- 全量 Node 测试、公开文档检查、web/mp 构建与 H5 200 全绿。
- Android 标准基座真实发送 PDF 成功；单击自发 PDF 直接打开，不显示远端下载 loading；接收 PDF 可下载并预览；删除消息或登出会释放本地副本。
